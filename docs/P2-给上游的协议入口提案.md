# P2 提案：Animaku 上游需要暴露的「协议入口」

> 目标：我们不 fork、不改 Animaku 源码（避免每次上游更新丢失/冲突），把它作为
> `git submodule` 固定版本引入，我们的增强代码全部放在独立目录，靠**上游主动暴露
> 的少量协议入口**实现「定时从 GitHub 更新 / 访问统计 / 多源失败自动刷新」等功能。
> 本文档列出**需要原作者加什么**，每一项都标明「为什么必须上游改、
> 我们自己在注入层做不了」以及「最小改动量」。
>
> **更新（2026-11-17）**：白色风格切换按钮已从我们的注入层删除，P2-1 的 `FRONT_THEME`
> 与 P2-3（主题 API 化）不再需要——上游已内置 light/dark 主题，够用。当前真正需要对接的
> 只剩 **P2-2（全局 hooks）** 和 **P2-4（SEO 配置化，即上游 issue #5）**。下文保留完整
> 原始分析，但提交 PR 时以第 5 节「精简后 PR 清单」为准。
>
> 依据：基于 Animaku master v1.30.2 真实源码分析，非臆测。对应上游 issue #5
> （SEO 文案写死、每次更新改动麻烦）是同一类痛点。

## -1. 先回答：我们现在到底要不要给原作者提 PR？

**当前不需要。** 我们这套架构（独立仓库 + submodule 只读引用上游 + 注入层）的设计目的，
就是**不改上游源码、不依赖原作者配合**。所有功能（设置页开关、统计、多源刷新、底部五栏）
都已通过注入层实现并在 `https://anime.map987.dpdns.org/` 线上验证通过。上游随便更新，
CI 自动 `submodule update --remote` 吸收，我们零冲突。

**什么时候才需要跟原作者对接 PR？** 只有当我们要把某个功能"从注入升级成上游原生支持"时：

| 情形 | 要不要提 PR |
|---|---|
| 继续用 submodule + 注入层（当前方式） | ❌ 不需要。上游更新自动吸收 |
| 想让某功能进入 Animaku 主线、被所有用户用到 | ✅ 提 PR（本文档的协议入口） |
| 注入层因 React 重渲染/内部状态拿不到而失效 | ✅ 提 PR（请上游暴露 hooks）|
| 想修上游自身的 bug（如 issue #5 SEO 写死） | ✅ 提 PR（P2-4）|

**结论**：PR 是"可选的长远合作路径"，不是当前开发的阻塞项。本文档是"如果决定提 PR，
要原作者加什么"的清单——把复杂的内部回调变成稳定的公开契约，让我们不用注入也能拿到数据。

提 PR 的 Git 协作机制（多人同时改、三方合并）见 `docs/Git三方合并与PR协作.md`。

## 1. 背景：为什么必须"上游开口 + 我们注入"而不是我们直接改

| 方案 | 上游更新后会怎样 | 结论 |
|---|---|---|
| 直接改 Animaku 源码（fork 后改） | 每次 `git submodule update` 覆盖我们的改动，或大规模 merge 冲突 | ❌ 不可持续（正是 issue #5 的痛点）|
| 只靠 DOM 注入（Tampermonkey 式） | React 19 重渲染会冲掉注入的 DOM；拿不到内部 store | ❌ 脆弱 |
| **上游暴露少量稳定协议入口 + 我们注入** | 协议入口是上游承诺的稳定契约，上游更新不会破坏 | ✅ 采用 |

核心矛盾：`apps/web` 是 Vite + React 19，`apps/server` 是 Hono。前端状态在
zustand store（`useSettingsStore`）和 React Router 里，纯 DOM 注入**拿不到也不改不了**
这些内部状态。所以关键功能（主题切换、设置页加开关）必须有上游的配合点。

## 2. 需要上游提供的协议入口（按优先级）

### P2-1【环境变量透传到前端】—— 对应 `FRONT_THEME=ON`

**需求**：把一组 `VITE_*` 构建期环境变量，原样透传到 `window.__ANIMAKU_CONFIG__`，
让我们部署时用一个开关就能启用/关闭注入功能，而不用改源码重新构建。

**为什么必须上游改**：Vite 里只有 `import.meta.env.VITE_*` 会被静态替换。我们要的开关
必须在**构建产物**里留一个读取点；纯注入拿不到 `import.meta.env`（已被编译成常量）。

**最小改动**（`apps/web/index.html` 加一段内联脚本 + `apps/web/vite.config.ts` 暴露 env）：

```html
<!-- index.html <head> 里，上游加这一段（约 12 行） -->
<script>
  window.__ANIMAKU_CONFIG__ = {
    frontTheme:    import.meta.env.VITE_FRONT_THEME ?? 'off',     // on | off
    autoRefresh:   import.meta.env.VITE_AUTO_REFRESH ?? 'off',    // 多源失败自动刷新
    trackStats:    import.meta.env.VITE_TRACK_STATS ?? 'off',     // 访问统计开关
    gitSync:       import.meta.env.VITE_GIT_SYNC ?? 'off',        // 设置页 Git 更新开关
    hooksEndpoint: import.meta.env.VITE_HOOKS_ENDPOINT ?? '',     // 我们的注入脚本地址
  };
</script>
```

配套：`vite.config.ts` 的 `define` 或 `envPrefix` 已支持 `VITE_`（Animaku 现成支持），
无需额外改。我们部署时只要在 EdgeOne 环境变量里设 `VITE_FRONT_THEME=on` 即可。

> 这就是你说的 `FRONT_THEME = ON` 的落地形态。上游只要把这个读取点留在 index.html，
> 剩下的主题实现（白色 switch / design 风格切换 UI）全部由我们的注入脚本做。

### P2-2【全局扩展点 window.__ANIMAKU_HOOKS__】—— 最关键

**需求**：在应用挂载前后，暴露一个稳定的全局对象，允许注入方注册回调。共 4 个钩子：

```ts
// 上游在 apps/web/src/main.tsx（或 App 挂载处）加约 20 行
declare global {
  interface Window {
    __ANIMAKU_HOOKS__?: {
      onRouteChange?: (path: string, search: string) => void   // 路由变化（统计"进入某动漫"频率）
      onSearch?: (keyword: string, source: string) => void      // 搜索频率
      onSourceSwitch?: (from: string, to: string, ok: boolean) => void // 换源/加载失败
      registerSettingsPanel?: (render: (host: HTMLElement) => void) => void // 设置页加自定义面板
    }
    __ANIMAKU_STORES__?: {
      settings?: typeof useSettingsStore   // 读/改主题等设置
      siteConfig?: typeof useSiteConfigStore
    }
  }
}
```

**为什么必须上游改**：React 内部组件（搜索框、路由、播放器换源逻辑）的回调，注入层
在外部无法拦截。必须由上游在这些动作发生处调用 `hooks.onSearch?.(...)` 等。

**上游调用点**（都是一行）：
- `App.tsx` 的路由 / `useLocation` 变化处 → 调 `onRouteChange`
- `SearchPage` 提交搜索时 → 调 `onSearch`
- 播放器换源成功/失败处 → 调 `onSourceSwitch`
- `SettingsPage` 末尾 → 留一个 `<div id="animaku-ext-settings">` 容器，注入方往里渲染

有了这 4 个钩子，我们要的**全部统计维度**（utm_source 分解、搜索频率、进入某动漫
频率、使用某入口频率）和**设置页 UI 注入**都能零冲突实现。

### P2-3【主题切换 API 化】—— 白色 switch / design 风格切换

好消息：**Animaku 已有主题系统**，我们不必从零要。现状：

- `apps/web/src/stores/settings.ts`：`AppTheme = 'dark' | 'light'`，`setTheme/toggleTheme`，
  应用到 `document.documentElement.setAttribute('data-theme', theme)`
- `VITE_DEFAULT_THEME` 构建期默认值
- `/api/site/config` 可下发 `defaultSettings.theme`
- `Switch` / `SwitchRow` 组件（`framer-motion` iOS 胶囊开关）现成

**需要上游补的（很小）**：

1. 把主题从二元 `dark | light` 扩成支持"我们的白色 switch 风格 / design 风格"两套 token：
   `AppTheme = 'dark' | 'light' | 'kz-white' | 'kz-design'`。CSS 里加两套
   `[data-theme="kz-white"]` / `[data-theme="kz-design"]` 变量块即可。
2. 设置页开关行复用现成 `SwitchRow`，加一个"界面风格"入口，调用 `setTheme`。
3. 暴露 P2-2 的 `__ANIMAKU_STORES__.settings`，让注入脚本能直接 `setTheme('kz-white')`。

> 如果你不想把我们的两套风格合进上游主线，也可以只要 P2-2 的 store 暴露，
> 我们在注入层自己 `document.documentElement.setAttribute('data-theme','kz-white')`
> + 注入自己的 CSS 变量块，效果一样，且完全不碰你的源码。

## 4. 附：多源加载失败——自动刷新 vs 弹窗（用户心理学结论）

你的问题：「加载失败弹出是否立即刷新，还是直接自动刷新？」

**结论：分场景，默认自动、特殊情况才提示，不要一律弹窗。** 依据：

1. **高频失败路径（切源、首集起播）→ 静默自动刷新**。用户在追番，心态是"赶紧播"，
   弹窗 = 打断 = 摩擦。自动重试 1 次（用户几乎无感）符合"最小努力原则"。
2. **手机端大拇指热区**：底部 1/3 屏是拇指自然覆盖区。自动刷新按钮若要做，放底部;
   但自动刷新本身不需要用户点，零操作最优。
3. **相邻设计**：刷新动作紧邻"换源"按钮（用户心智里两者是同一件事），不要放到设置页。
4. **只有反复失败（≥2 次）才提示**：用底部轻提示（非模态、可点"换源"），不要用阻塞式
   模态框。模态框只在他明显卡住时用，且给"一键换源"主按钮（拇指热区）。

实现：`onSourceSwitch(from,to,ok=false)` → 计数，第 1 次静默重试，第 2 次弹非模态提示。
这套逻辑全在我们的注入层，不需要上游改。
