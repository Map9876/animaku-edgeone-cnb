# Git 三方合并与 PR 协作（给上游提 PR 用）

> 这篇讲「fork 热门仓库 → 改代码 → 提 PR」时，别人也在同时改，为什么不会乱、为什么能推送。
>
> **先区分两个场景，别搞混：**
> - **本文场景**：给 Animaku 上游提 PR（P2 提案），需要 fork + 改上游代码 + 提 PR。
> - **本项目现状**：`kfc50/animaku-edgeone` 是**独立仓库 + submodule 只读引用上游**，
>   我们**从不改上游源码**，所以本项目内部不存在 fork 冲突问题（见 README）。
>
> 本文是给「将来给 Animaku 提 PR」准备的知识。

---

## 一、核心问题

热门仓库每天很多人同时提 PR。常见担忧：

```
T0：热门仓库 master = A
  ├─ 你 fork 一份，从 A 开始改，改了 1 小时
  └─ 另一个人也从 A 开始改

T1：别人先改完，提 PR，上游合并 → master 变成 B
T2：你改完了想提 PR —— 你的 fork 还停在 A，上游已经 B 了
```

**结论：这完全正常，不会推不上去。** 因为 PR 不是"覆盖整个仓库"，而是提交一个**差异（diff）**，
上游把你的 diff **合并**到最新的 B 上。

---

## 二、为什么"行号变了"也不怕——三方合并

### 关键认知：Git 不按"第几行"记改动，按"内容"记

```
A 版本：
  第8行:  香蕉
  第10行: 苹果

B 版本（别人改完，还加了一行 → 你的"苹果"挪到第11行）：
  第8行:  香蕉 → 葡萄
  第11行: 苹果        ← 行号从 10 变 11，但内容还是"苹果"

你的 fork（基于 A）：
  第10行: 苹果 → 橘子
```

别人加了一行，你的"苹果"在 B 里行号变了。但 Git 不怕——它认得"苹果这行内容跑哪去了"，不死记行号。

### 三方合并（three-way merge）

Git 合并时有**三分信息**：

```
        共同祖先 A（你俩都从这里分叉）
         /          \
你的版本            别人的版本
(苹果→橘子)          (香蕉→葡萄 + 加一行)
```

Git 的算法：
1. 算出**你相对 A 做了什么**：`苹果 → 橘子`（一个补丁）
2. 算出**别人相对 A 做了什么**：`香蕉 → 葡萄` + 加一行（另一个补丁）
3. 判断两个补丁能不能叠加：
   - 你动"苹果"那处，别人动"香蕉"那处 + 别处加行 → **不同位置** → 两处都保留，自动合并 ✓

### "共同祖先"是基石（这是最关键的一点）

Git 不是只看到 B 和你的版本两个**结果**，它记得你俩**都从 A 分叉**的那一刻（merge base）。
所以它能反推：

- "你的橘子" 源自 "A 的苹果"
- "B 的葡萄" 源自 "A 的香蕉"
- 在 A 里这是两个不同位置 → 在 B 里也应是两个独立改动 → 可合并

**没有共同祖先，Git 只能瞎猜；有了它，Git 能精确知道每个改动"源自哪里、改了什么"。**

### "减2加2"的比喻

Git 把每个版本相对共同祖先表示成一串"删了什么、加了什么"（补丁/diff），
然后看两个补丁能不能叠在一起。**单位是"内容块"，不是"行号"**。
这就是你说的"减2加2"——本质是补丁的加减运算。你那个理解是对的。

## 三、什么时候才真冲突

只有当**两个人改了同一个内容块**（都把"苹果"改了，一个改"橘子"一个改"梨"）：

- Git 算出两个补丁都作用在"苹果"这一处，且结果不同
- 它无法自动决定用谁的 → 报冲突 → 需要人手动选

热门项目里这种情况**反而少见**——大家改的功能模块通常不同。
即使发生，也只是那几行需要手动解决，不影响其他改动。

## 四、实际操作流程（应对"这中间别人改了"）

```bash
# 1. fork 后，给本地加一个指向上游的 remote（只需一次）
git remote add upstream https://github.com/uerax/Animaku.git

# 2. 提 PR 前，先同步上游最新代码
git fetch upstream
git checkout master
git merge upstream/master      # 或 git rebase upstream/master

#    - 没改同一处 → 自动合并，无感
#    - 改了同一处 → 提示冲突，手动解决那几行，然后 git add + git commit

# 3. push 到你的 fork，提 PR
git push origin your-branch
```

**核心动作就一个：提 PR 前先 `merge/rebase` 上游最新代码**（叫"同步上游"），这是每个 PR 提交者的日常。

## 五、用类比记住

想象一条河（master）在流：

- 你从上游舀了一桶水（fork @ A），在自己桶里加料（改代码）
- 别人也舀了一桶，先倒回河里（他的 PR 先合并，河变成 B）
- 你倒回去之前，先把河里新流来的水也舀进你的桶（merge upstream），搅匀
- 再倒回去（提 PR）——你的料 + 河里原有的水都在

只有当**你俩往桶里同一个位置各加了一种料**，才需要你手动决定留哪个。

---

## 六、一句话总结

> PR 是提交 diff 不是覆盖；Git 基于**共同祖先**做三方合并，按**内容**而非行号计算补丁加减；
> 不同人改不同地方自动合并，只有改同一处才冲突；提 PR 前先同步上游即可。
> 所以"两人同时改热门项目"是常态，Git 从机制上就支持。
