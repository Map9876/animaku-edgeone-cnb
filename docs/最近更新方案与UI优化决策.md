# 第一部分：「最近更新」实时服务

## 1. 为什么原项目做不到"3 分钟前更新"

Animaku 的原理（看源码确认）：**它本身不存番剧的更新时间**，而是当用户点进某部番、或搜索时，
才拿 Bangumi/原站的 ID 去**实时请求源站**解析播放链接。所以：

- 它没有"全站番剧的最新更新时间"这个数据集——数据是按需拉取、用完即弃的。
- 首页的"每日放送/排行榜"是 Bangumi 的静态元数据，不是"5 分钟前更新了第几集"这种实时信号。
- 想显示"X 分钟前更新"，必须**有人持续地、主动地去轮询各源站**，维护一份带时间戳的数据。

这正是你要补的缺口。

## 2. 你这个方案的本质：需要一个"常驻爬虫 + 推送服务"

你要的东西，抽象出来是：

```
10+ 个源站  ──每分钟轮询──>  爬虫服务（维护"最新更新"数据库）
                                   │
                                   │ WebSocket / SSE 推送
                                   ▼
                            客户端（我们的 Animaku 发行版）
                                   │
                                   ▼
                        首页显示"X 分钟前更新 / 今日更新"
```

关键点：**这必须是一个常驻服务**（长期运行、定时执行），不能是纯静态站点。

## 3. 部署选型对比（你问的 CF / EdgeOne / GitHub Cron / CNB 临时域名）

| 方案 | 能否常驻+定时 | 费用 | 动态 IP 问题 | WebSocket | 适合度 |
|---|---|---|---|---|---|
| **CF Workers + Cron Triggers + D1/KV** | ✅ 原生 cron（可精确到分钟） | 免费额度大 | 无固定 IP 问题（边缘运行） | WS 需 Durable Objects | ⭐⭐⭐⭐⭐ 最合适 |
| **CNB 云原生开发环境 + crontab** | ✅ 但需常驻容器 | 免费额度有限 | 临时域名每 18h 变、且限 10 IP | 需自己起 WS | ⭐⭐ 个人玩具可行，生产不稳 |
| **GitHub Actions Cron** | ⚠️ 定时但最少 5 分钟粒度、且延迟大 | 免费 | 无 IP 问题 | 不能常驻 WS（只能写仓库文件） | ⭐⭐⭐ 适合低频同步 |
| **EdgeOne Pages Functions** | ⚠️ 函数按需触发，无原生 cron | 免费 | 无 IP 问题 | 边缘函数 WS 受限 | ⭐⭐ 做接收端可以，做爬虫调度不行 |
| **自有服务器 + cloudflared tunnel + EO 加速**（fis.ink 那篇） | ✅ 完全可控 | 一台机器 | tunnel 无固定 IP 但域名固定 | 原生 WS 随便用 | ⭐⭐⭐⭐ 最灵活，但要养机器 |

## 4. 破局点：你的几个纠结，逐个解

### 4.1 CNB 临时域名为何不适合（你的判断是对的）

- 临时域名每 18 小时变 → 客户端要动态获取，服务端内置 CNB_TOKEN 去查——能做但脆。
- **限 10 个 IP** → 如果部署在动态 IP 环境（你说的 1.1.1.1 之类），这 10 个 IP 名额会被动态变化耗尽/误判。
- 结论：**只适合单人临时调试，不适合"服务端—客户端"的稳定链路**。你自己也意识到"个人访问也不行"——对。

### 4.2 "部署在动态 IP 里" → 用 Cloudflare Tunnel 解决（fis.ink 那篇的核心）

fis.ink 那篇文章解决的正是你的问题：**本地/内网服务没有固定公网 IP，如何稳定对外**：

```
你的爬虫服务（跑在家里/任意机器，动态 IP）
   │  cloudflared tunnel 主动外连（不需要公网 IP、不需要开端口）
   ▼
Cloudflare 给用户域名（固定，形如 xxx.trycloudflare.com 或自定义域）
   │
   ├─（可选）EdgeOne 再套一层 CDN + 免费 HTTPS（国内加速）
   ▼
客户端访问固定域名
```

- tunnel 是**服务主动向外连**，所以不管你的 IP 怎么变，域名不变。
- 注意 fis.ink 那篇的关键坑：**穿透用一个子域名，EO 加速用另一个子域名**，别混。
- Cloudflare 域名绑定**不需要信用卡**（免费套餐 + tunnel 免费）。

### 4.3 三篇文章和你的 CF/EO 通用反代理有什么区别（你"一直没懂"的点）

**一句话**：它们都是"谁在前、谁在后、谁加速谁"的不同排列组合。

| 文章 | 架构 | 解决什么 | 和 `kfc50_edgeone_proxy` 的区别 |
|---|---|---|---|
| **fis.ink** | 本地服务 → CF tunnel → EO CDN | 内网服务稳定对外 + 国内加速 | proxy 是"URL 代理"（转发请求到任意目标）；tunnel 是"反向穿透"（把本地服务暴露出去），两者方向相反 |
| **catcat** | 境内 EO / 境外 CF 分流同一个域名 | 全球访问都快 | proxy 是单出口转发；这个是 DNS 分线路把用户导到不同 CDN |
| **antwen** | R2 对象经 EO vs ESA 下载实测 | 大文件分发性能 | proxy 转发流媒体/文件；这篇是选 CDN 档位，跟代理无关 |

**你一直没懂的本质**：
- **CDN（EO/CF）** = 缓存 + 加速 + 隐藏源站，**不改变请求目标**，用户以为在访问 CDN，实际 CDN 替你去源站取。
- **JS Worker 反代理（kfc50_edgeone_proxy）** = 请求打到一个函数，函数**代替你去请求另一个 URL** 再把结果返回，路径本身就是目标地址（`/https://目标`）。
- **Tunnel** = 在**没有公网 IP 的内网服务**和**公网域名**之间打一条出站隧道，让公网能访问到内网服务。

三者是不同层的东西：代理是"应用层转发"，CDN 是"网络层缓存加速"，tunnel 是"网络打通"。

### 4.4 爬虫服务到底放哪——推荐方案

**推荐：CF Workers + Cron Triggers + D1**（你的"每分钟爬 10+ 源"需求的最佳匹配）：

- **Cron Triggers**：原生支持分钟级定时（`*/1 * * * *`，付费版可每秒），无需常驻服务器。
- **D1/KV**：存"番剧 ID → 最新集数 → 更新时间戳"，天然带时间。
- **Worker**：每次 cron 触发时并发请求 10+ 源站，解析后写 D1。
- **推送**：Worker 不能常驻 WS，但客户端可以**轮询 `/api/latest-updates`**（每分钟一次）或 Worker 写完后触发 SSE。对"最近更新"这种分钟级数据，**轮询完全够用**，不必强上 WebSocket。

> 你的直觉"每 18 点到次日 3 点每分钟爬"——Cron Triggers 可以直接写表达式限制时段，比 CNB crontab 优雅得多。

**为什么不用 EdgeOne 做爬虫**：EdgeOne Pages Functions 没有原生 cron，函数按需触发，做"每分钟主动爬"不顺手。EdgeOne 适合做**前端 CDN**（我们现在就在用）。

**最低成本起步**：先用 CF Worker + Cron（免费额度足够 10+ 源每分钟一次的小规模），把数据写 D1，前端加个 `/api/latest-updates` 轮询。跑通后再决定要不要上 tunnel/WS。

## 5. 推荐落地路线（分阶段）

1. **阶段 1（验证）**：CF Worker + Cron 每 5 分钟爬 3 个主力源，写 KV，暴露 `GET /latest`。
2. **阶段 2（接入）**：我们的 EdgeOne 发行版前端加一个组件，轮询这个 endpoint，首页显示"今日更新 / X 分钟前"。
3. **阶段 3（扩源+加密）**：扩到 10+ 源、分钟级、加 utm 统计；如需真·实时再上 Durable Objects WebSocket。
4. **阶段 4（可选）**：若某源站 CF 直连不通，用 tunnel + EO 加速那条路做中继。

## 7. 信息密度压缩（AI 项目通病）

**问题**（你指出的）：Animaku 是 AI 写的，卡片间距大、分类上下空白多、要下滑很久才看到卡片。

**参考 B站索引页**（视频第 25 秒）：
- 三列网格、卡片紧凑、评分/话数直接压在封面上；
- 标题+副标题两行截断；分类横滑；榜单按"更新至 X 话"组织。

**做法**（注入 CSS 覆盖，不碰上游）：
- 缩小网格 gap（如 `gap: 8px`）、卡片 padding/margin；
- 压缩分类区间距、section 之间的空白；
- 标题字号/行数微调，让首屏塞进更多卡片；
- 用浏览器截图前后对比验证。

> 注意：这类"视觉密度"改动必须真实浏览器截图肉眼核对（记忆里的铁律），不能只看 CSS 就宣称完成。

## 8. 一句话总结

- **最近更新**：原项目按需拉取、不存时间戳，所以做不到；补一个"常驻爬虫 + 时间库"服务。
  最佳落点是 **CF Workers + Cron + D1**，前端轮询即可，不必强上 WebSocket；动态 IP 问题用
  Cloudflare Tunnel（fis.ink 那篇）解决，CNB 临时域名只适合玩具。
- **CDN vs 代理 vs Tunnel**：缓存加速 / 应用层转发 / 网络打通，三层不同东西。
- **UI**：胶囊悬浮底栏 + 压缩信息密度，都在注入层做，不碰上游源码。
