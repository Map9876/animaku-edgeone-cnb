# 排行榜与统计体系决策（2026-11-18）

## 先摆事实（都是实测/读码确认，不是猜）

### 事实 1：上游已经有完整的排行榜 API
v1.30.5 的 `apps/server/src/routes/stats.ts` 里现成有：
```
GET /api/stats/rank          (total, top20)
GET /api/stats/rank/today    GET /api/stats/rank/week
GET /api/stats/rank/month    GET /api/stats/rank/total
GET /api/stats/subject/:id   GET /api/stats/online
```
基于 `watchStatsRepo.getTopRankings(type, limit)`，底层是 **SQLite**。
你说的"播放量是最近一两个版本才加的"——对，rank 这组端点是 v1.30.x 新加的。

### 事实 2：我们线上的排行榜是空的
```
/api/stats/rank      → {"data":[]}
/api/stats/rank/today → {"data":[]}
/api/stats/online    → {"online":0}
```
**根因**：EdgeOne 无状态运行时，`node:sqlite` 被我们的 `runtime/sqlite-stub.ts` 替换成 no-op
（`run/get/all` 全空、`getDatabase()` 不可用）。上游 stats 写入走不通，所以排行榜恒空。
这不是 bug，是"上游用 SQLite、EdgeOne 没有 SQLite"的架构冲突。

### 事实 3：我们自己已有一套完整的统计（只是和排行榜没打通）
`runtime/analytics.ts` + `inject/analytics.js`：
- `POST /api/track`：事件写进 **EdgeOne Blob**（`animaku-analytics/events/*`），字段
  `utm_source / entry / fromPage / toPage / subjectId / did / ts`
- `GET /api/stats`：读 Blob 聚合，输出 `byUtmSource / byEntry / 页面流转 / subject 频率 / 时间趋势`
- 前端已埋：utm 来源、设备 id(did)、路由跳转、搜索、换源成功/失败、进入番剧详情

这套是**我们自己的**、跨部署持久的、真实在收数据。只缺"把它呈现成排行榜/播放量"。

### 事实 4：Animaku 的规则确实源自 Kazumi 体系（你猜对了）
克隆 `Predidit/KazumiRules`（87 个 JSON）对比 Animaku `default-plugins`（21 个 JSON）：
两边字段几乎逐一对应——`api/type/name/version/muliSources/useWebview/useNativePlayer/
userAgent/baseURL/searchURL/searchList/searchName/searchResult/chapterRoads/chapterResult`。
Animaku 只多了 `weight/titlePreference/usePost/referer`。
结论：Animaku 的源规则体系就是 Kazumi 那套（或 AI 参考了它）。Kazumi 有 87 源，Animaku 只用了 21 个。
但——**这跟"播放量"无关**。Kazumi 规则里没有任何播放量字段，它只描述"怎么搜索/解析"。

### 事实 5：上游源码里没有"从源站抓播放量"的逻辑
grep 播放量/viewCount/playCount-source 都没有。原站排行榜的数据来源是**它自己的访问统计**
（用户点播放 → SQLite +1），不是去各视频站抓别人的播放量数字。

---

## 关键区分：这里其实混了三种完全不同的数据

| 数据 | 是什么 | 谁在产生 | 现状 |
|---|---|---|---|
| **A. 内容热度/播放量** | 哪些番剧火 | 用户播放行为（原站 SQLite / 我们 Blob）| 原站有，我们空 |
| **B. 访问行为统计** | 用户从哪来、点了什么 | 前端埋点 → 我们 Blob | ✅ 已在收 |
| **C. 源站播放量** | 各视频网站显示的播放数字 | 去爬别人的站 | 原站没有，也不打算有 |

你的诉求把 A/B/C 揉在一起了。拆开之后，难度和必要性天差地别：
- **A+B**：我们自己的数据，打通即可，成本低、真实可信
- **C**：爬第三方数据，合法性/准确性/维护成本都高，且原站根本没做——**这是你在开新战场，不是"同步上游"**

## 我的判断（逐条回应你的问题）

### Q1：上游更新后，排行榜能自动一致吗？
**代码能同步，数据不能。** rank 这组 API 会随 submodule 自动更新到我们 bundle（已验证 CI 正常构建），
但它依赖 SQLite，EdgeOne 上恒空。想让排行榜有数据，必须**把数据源从 SQLite 换成我们的 Blob**——
这是个明确的适配，能做，见 P0。

### Q2：加一个"和原站同样 UI 的播放量展示"，要更多名次
**该做，而且应该复用上游的 UI 和数据契约，不是另起炉灶。** 上游前端已经有排行榜页面组件，
CI 同步后 UI 自动就是最新的。我们要做的只是让 `/api/stats/rank*` 返回我们的真实数据。
"原站只显示前三"是上游前端的 limit，我们可以在自己的 bundle 注入层把 limit 调大，或单独做个展示页。

### Q3：统计每个入口的访问量（首页大图、热门、从 /anime /timeline 进详情）
**部分已经有了**（路由跳转 + entry 字段在收）。缺的是"页面内具体点哪张卡片"。
trace 文档的建议方向是对的：**稳定事件名 + 封装 track() 适配层 + 不靠 DOM 选择器**。
但我们不需要引入 PostHog/Umami（重、要外部服务、破坏"不改上游"），在现有 analytics.js 上补
几个点击埋点即可。这是 P1。

### Q4：做一级页面展示"各来源网站播放量"+白名单筛选
**建议先不做。** 理由：
1. 这是爬第三方数据（C 类），和"同步上游"是两码事，原站自己都没做
2. 白名单要人工维护 + 持续验证"哪些源的播放量真实、哪些是评分冒充的"——长期负担
3. 播放量数字的准确性、时效性、合法性都存疑，做成一级页面会误导用户
4. 你自己也说"调研不一定对、别太受它影响"——这个判断是对的
如果要做，正确形态是**统计页里的一个 tab**，标注"数据来自第三方，仅供参考"，而不是一级导航。放到 P2。

### Q5：要不要给原站提 PR（让它显示更多/提供协议）
**现在不提。** 排行榜 API 上游已经有了；我们要的"数据源换成无状态可适配"会侵入它的 SQLite 核心，
而且你之前明确说后续还要加更多钩子，现在提会被推翻。我们在自己的 bundle 层适配即可，零冲突。

## 建议执行顺序

### P0（最该做，解决"线上排行榜空"这个实际问题）
把 `/api/stats/rank*` 的数据源从 SQLite 适配到我们的 Blob：
- 定义"播放量" = 进入 `/play/:id` 或 subject 详情的去重 did 访问（我们 Blob 已有 subjectId/did）
- 在 `analytics.ts` 里加 rank 聚合，按 today/week/month/total 分组
- 用构建期注入把 `statsRoutes` 的 `getTopRankings` 换成读我们 Blob
- 效果：线上排行榜立刻有真实数据，且随上游 UI 更新自动一致

### P1（补齐入口点击统计）
在 `inject/analytics.js` 补：首页 hero 点击、热门/分类卡片点击、从 /anime /timeline 进详情的归因。
沿用现有 Blob 通道，不引外部分析平台。

### P2（暂缓，需要时再做）
各来源网站播放量 + 白名单。若做，做成统计页 tab，不做一级页面。

## 一句话总结

**别爬别人的播放量（C），先把自己已有的访问数据（A+B）打通成排行榜**——
这是最快、最真实、最省维护的路，而且能和上游 UI 更新保持一致。
Kazumi 同源性只是印证了"规则从哪来"，跟播放量无关。
